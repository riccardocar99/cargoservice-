LABORATORIO DI INGEGNERIA DEI SISTEMI SOFTWARE

Introduction

Questo documento descrive il lavoro svolto nello Sprint 2 per lo sviluppo del sistema cargoservice.

Goal dello Sprint 2

L'obiettivo (Goal) dello Sprint 2 è lo sviluppo e l'integrazione di rete dei componenti fisici/simulati distribuiti del sistema, superando i mock dello Sprint 1: la WebGUI dell'IOPort (che racchiude pushbutton e display) ed il sotto-sistema Sonar & Led su Raspberry Pi Pico W comunicante via MQTT. Il corretto funzionamento distributivo e la gestione delle anomalie di rete devono essere convalidati.

Requirements

Il testo dei requisiti finali del tema è consultabile nel file di specifica fornito dal committente: Tema2026.html

Requirement analysis | Vocabolario

Dall'analisi dei requisiti dello Sprint 0 e dall'architettura dello Sprint 1, emergono i seguenti requisiti per la distribuzione:

  • IOPort (WebGUI): Deve esporre l'interfaccia utente formata dal pushbutton (input) per richiedere il carico e dal display (output) per mostrare lo stato del hold e i messaggi di stato.
  • Sonar & Led (PicoW): Il sonar rileva la presenza del container (distanza D < DFREE/2 per 3s) e gestisce l'anomalia di fuori servizio (D > DFREE per 3s). Il Led lampeggia mentre il sistema è impegnato (engaged) ed è spento altrimenti.

Problem analysis

Interazione della WebGUI (IOPort) con Qak

La WebGUI dell'IOPort deve poter inviare la richiesta load e mostrare dinamicamente lo stato. Poiché gli attori QAK sono nativamente risorse CoAP osservabili, la WebGUI (implementata in HTML5/JavaScript) può registrarsi come Observer CoAP sul risorsa /ctx_cargoservice/cargoservice. In questo modo riceverà aggiornamenti asincroni push (senza polling) ad ogni variazione di stato. Le richieste di carico verranno invece inoltrate tramite messaggi CoAP Request o chiamate HTTP/REST.

Comunicazione del Nodo Sonar & Led (PicoW)

Il microcontrollore Raspberry Pi Pico W controlla i dispositivi fisici eseguendo script MicroPython. La comunicazione avviene via rete tramite protocollo MQTT (broker centralizzato):

  • Il Sonar legge i dati fisici dal sensore HC-SR04 ed effettua la pubblicazione MQTT delle letture di distanza.
  • Il Led si sottoscrive ad un topic MQTT dedicato (es. cargoservice/led) per accendersi o lampeggiare in risposta alle transizioni dell'orchestratore.

Per isolare l'orchestratore cargoservice dai dettagli del protocollo MQTT, introduciamo un attore ponte (MQTT Adapter) nel contesto ctx_cargoservice che si occupa di convertire i messaggi MQTT in messaggi nativi QAK (es. distance(D)) e viceversa.

Architettura Logica Distribuita e Nodi di Deployment

In coerenza con la pianificazione e l'analisi effettuata nello Sprint 0, il deployment effettivo del sistema si distribuisce sui seguenti contesti fisici ed hardware:

  • PC Principale (Host PC): Rappresenta il nodo centrale computazionale del sistema. Su questa macchina fisica coesistono ed operano due diversi runtime:
    • Java Virtual Machine (JVM): Ospita il processo principale cargoservice (eseguito via ./gradlew run alla porta CoAP 8082). Questo processo avvia ed ospita nativamente il web server IOPortWebServer per la WebGUI dell'IOPort (porta 8081).
    • Docker Engine: Gestisce l'intera infrastruttura di simulazione e di comunicazione di rete tramite container isolati sulla stessa macchina:
      • Il broker MQTT mosquitto (porta 1883), impiegato per lo scambio messaggi con il microcontrollore.
      • Il pianificatore di movimenti autonomo robotsmart26 (contesto esterno ctxrobotsmart, porta 8020).
      • L'interfaccia di monitoraggio 2D del robot robotoutgui25 (porta 8085).
      • Il simulatore fisico 3D wenv (porte 8090/8091).
  • Web Browser (Client GUI): Rappresenta l'interfaccia utente finale per l'operatore/cliente. Dal browser vengono caricate e renderizzate la dashboard dell'IOPort (indirizzo http://localhost:8081, che comunica con la JVM tramite CoAP) e l'interfaccia 2D del robot (indirizzo http://localhost:8085, che comunica con Docker via WebSocket).
  • Raspberry Pi Pico W (Nodo Remoto): Rappresenta il microcontrollore remoto hardware (contesto ctx_picow) deputato all'interfacciamento fisico. Esegue uno script MicroPython autonomo che legge le distanze dal sensore Sonar (HC-SR04) e pilota lo stato del Led fisico, scambiando informazioni con il broker MQTT (porta 1883) esposto dal PC Principale.

Modellazione del Comportamento del Robot e Coordinamento

Nel contesto dello Sprint 2, l'orchestratore cargoservice e l'attore cargorobot coordinano la movimentazione del robot nel rispetto dei requisiti di tema finale. Il robot esegue la transizione tra le aree logiche (IOPort, Slot5 e Slot di stoccaggio) e supporta la sospensione/ripristino dei movimenti in caso di guasto rilevato dal sonar remoto.

1. Sincronizzazione e Reset Iniziale

All'avvio, l'orchestratore invia un comando di reset per riallineare il planner logico di robotsmart26 con lo stato di startup del simulatore 3D (WEnv), forzando la posizione iniziale a (0,0) con direzione SUD (down):

State s0 initial {
    println("cargoservice | starting...") color blue
    [# SystemOutOfService = false #]
    forward ioport -m display_msg : display_msg(service_working)
    println("cargoservice | Sincronizzazione: resetto lo stato del robot nel planner a (0,0) SOUTH...") color blue
    forward robotsmart -m setrobotstate : setpos(0, 0, down)
    updateResource [# "state($SystemOutOfService,$Slot1Occupied,$Slot2Occupied,$Slot3Occupied,$Slot4Occupied,$ReservedSlot,$IOPortOccupied,$DisplayMsg)" #]
}

2. Mappatura delle Coordinate Logiche della Stiva

Le coordinate della stiva seguono la convenzione del planner A* espressa come (riga, colonna). Per ciascuno slot logico viene definita la coordinata di posizionamento adiacente libera ("accanto") al fine di prevenire collisioni con i container o gli ostacoli strutturali:

when (CurrentDest) {
    "home"   -> { TargetX = 0; TargetY = 0 } // Riga 0, Colonna 0
    "ioport" -> { TargetX = 4; TargetY = 0 } // Riga 4, Colonna 0 (IOPort)
    "slot5"  -> { TargetX = 2; TargetY = 5 } // Cella libera accanto a destra dello Slot 5 (2,4)
    "slot1"  -> { TargetX = 1; TargetY = 1 } // Cella libera accanto a sinistra dello Slot 1 (1,2)
    "slot2"  -> { TargetX = 2; TargetY = 3 } // Cella libera accanto sotto allo Slot 2 (1,3)
    "slot3"  -> { TargetX = 3; TargetY = 1 } // Cella libera accanto a sinistra dello Slot 3 (3,2)
    "slot4"  -> { TargetX = 4; TargetY = 3 } // Cella libera accanto sotto allo Slot 4 (3,3)
    else     -> { TargetX = 0; TargetY = 0 }
}

3. Sequenza Nominale e Ciclo di Lavoro

Il robot esegue la transizione lineare dei carichi passando per lo slot5 per la marcatura temporanea:

// 1. Spostamento all'IOPort per raccogliere il container
State robotExecution {
    [# CurrentDest = "ioport" #]
    request cargorobot -m move_robot : move_robot(ioport)
}
Transition t0 whenReply move_done -> robotAtIOPort

// 2. Spostamento a Slot 5 per etichettatura temporanea
State robotAtIOPort {
    [# CurrentDest = "slot5" #]
    request cargorobot -m move_robot : move_robot(slot5)
}
Transition t0 whenReply move_done -> robotAtSlot5

// 3. Posizionamento e attivazione del marcatore
State robotAtSlot5 {
    println("cargoservice | robot arrivato in slot5: poso temporaneamente per marcatura...") color green
    forward marker -m start_marking : start_marking($ReservedSlot)
}
Transition t0 whenMsg marking_done -> markingCompleted

// 4. Trasferimento nello slot di stoccaggio definitivo
State markingCompleted {
    [# CurrentDest = ReservedSlot #]
    println("cargoservice | marcatura completata: sposto il container in $ReservedSlot...") color green
    request cargorobot -m move_robot : move_robot($ReservedSlot)
}
Transition t0 whenReply move_done -> robotAtReservedSlot

4. Gestione delle Interruzioni (Out of Service) e Ripristino

Nel caso in cui il Sonar rilevi un errore (distanza > DFREE per 3s), viene emesso l'evento alarm per arrestare immediatamente il robot virtuale. Al ripristino delle condizioni normali, l'orchestratore ricalcola la transizione riprendendo il movimento verso l'ultimo target di destinazione memorizzato (CurrentDest):

State handleInterrupt {
    println("cargoservice | INTERRUPTION: Sonar failure reported.") color red
    emit alarm : alarm(sonar_failure) // Arresta robotsmart26
    [# SystemOutOfService = true; DisplayMsg = "out_of_service" #]
    updateResource [# "state(...)" #]
} Goto outOfService

State handleRecovery {
    println("cargoservice | RECOVERY: Sonar reports normal operation.") color green
    [# SystemOutOfService = false; DisplayMsg = "service_working" #]
    updateResource [# "state(...)" #]
} Goto working if [# ReservedSlot == "" #] else resumeActivity

State resumeActivity {
    println("cargoservice | resuming movement to destination: $CurrentDest")
}
Goto robotExecution if [# CurrentDest == "ioport" #] else checkSlot5Resuming

Test plans

I test di integrazione dello Sprint 2 mirano a convalidare il comportamento distribuito simulando gli input in rete:

Test Funzionale 1: Pressione Pushbutton da GUI
Azione: La WebGUI invia una richiesta CoAP di load.
Risultato Atteso: Il display mostra la prenotazione dello slot logico e il led inizia a lampeggiare.
Test Funzionale 2: Rilevamento Sonar in Rete
Azione: Il Sonar pubblica via MQTT una distanza `D = 5` per 3 secondi.
Risultato Atteso: `cargoservice` riceve il messaggio, attiva la movimentazione del robot e il Led continua a lampeggiare.
Test Funzionale 3: Gestione Anomalie (Out of Service)
Azione: Il Sonar rileva una distanza `D > DFREE` (es. 30) per 3 secondi.
Risultato Atteso: Il sistema interrompe la movimentazione del robot, il display mostra `"Out of service"` ed il Led si accende fisso.

Deployment

Il deployment ed avvio del sistema si compone dei seguenti passi operativi:

  1. Avvio dell'Infrastruttura (Docker): Eseguire il comando docker compose up nella directory radice dello Sprint 2 per istanziare congiuntamente il broker MQTT mosquitto (porta 1883), il simulatore wenv (porte 8090/8091), il visualizzatore 2D robotoutgui25 (porta 8085) ed il pianificatore di movimenti robotsmart26 (porta 8020).
  2. Avvio del Nodo Fisico/Remoto (PicoW): Caricare ed eseguire lo script MicroPython/Python sul Raspberry Pi Pico W per collegare i sensori sonar e led al broker MQTT.
  3. Avvio del Core Business Logic: Eseguire il comando ./gradlew run per avviare il contesto software principale ctx_cargoservice (porta 8082), che attiva anche il web server dell'IOPort alla porta 8081.
  4. Interfacce Utente: Accedere tramite browser web alla dashboard dell'IOPort all'indirizzo http://localhost:8081 per inviare i comandi di carico, e monitorare i movimenti del robot all'indirizzo http://localhost:8085.
