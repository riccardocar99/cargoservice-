LABORATORIO DI INGEGNERIA DEI SISTEMI SOFTWARE

Introduction

Questo documento descrive il lavoro svolto nello Sprint 3 per lo sviluppo del sistema cargoservice.

Goal dello Sprint 3

L'obiettivo (Goal) dello Sprint 3 è il deployment distribuito ed il collaudo di rete dei componenti del sistema su dispositivi hardware reali (tranne il robot, che rimane virtuale come da requisiti di progetto). In particolare, questo sprint focalizza su:
  • Configurazione delle connessioni di rete reali: i vari nodi (PC principale, client WebGUI remoto, Raspberry Pi Pico W remoto) comunicano via rete LAN locale, superando i binding locali (localhost).
  • Deploy dello script MicroPython sul microcontrollore hardware reale Raspberry Pi Pico W (connesso fisicamente a Sonar HC-SR04 e Led).
  • Accessibilità distribuita della WebGUI dell'IOPort da parte di un PC client remoto connesso sulla stessa rete.

Requirements

Il testo dei requisiti finali del tema è consultabile nel file di specifica fornito dal committente: Tema2026.html

Requirement analysis | Vocabolario

Dall'analisi dei requisiti dello Sprint 0 e dall'architettura dei precedenti sprint, emergono i seguenti vincoli di deployment di rete:

  • Rete LAN Comune: Tutti i dispositivi (PC Principale, Client WebGUI, Pico W) devono essere connessi alla medesima sottorete Wi-Fi/LAN per poter effettuare il routing IP.
  • MQTT Broker Remoto: Il broker MQTT (Mosquitto) risiede sul PC Principale (in Docker) ma deve accettare connessioni sulla porta 1883 da parte del microcontrollore remoto.
  • IOPort Web Server: L'IOPortWebServer deve esporre la WebGUI (porta 8081) all'esterno dell'Host PC per permettere il caricamento da browser remoti.

Problem analysis

Interazione della WebGUI (IOPort) con Qak

La WebGUI dell'IOPort deve poter inviare la richiesta load e mostrare dinamicamente lo stato. Poiché gli attori QAK sono nativamente risorse CoAP osservabili, la WebGUI (implementata in HTML5/JavaScript) può registrarsi come Observer CoAP sul risorsa /ctx_cargoservice/cargoservice. In questo modo riceverà aggiornamenti asincroni push (senza polling) ad ogni variazione di stato. Le richieste di carico verranno invece inoltrate tramite messaggi CoAP Request o chiamate HTTP/REST.

In un contesto distribuito (es. browser aperto su un PC differente da quello in cui gira il servizio principale):

  • L'interfaccia utente web effettua chiamate HTTP relative (come /status e /load), che vengono risolte automaticamente verso l'indirizzo IP del PC Principale (su cui gira il server IOPortWebServer).
  • La JVM del PC Principale gestisce localmente le interazioni CoAP tramite localhost:8082 per connettersi a `cargoservice`, disaccoppiando completamente il browser client dai dettagli del protocollo CoAP.

Comunicazione del Nodo Sonar & Led (PicoW) ed Emulatore

Nello Sprint 3, il codice viene eseguito direttamente sul microcontrollore hardware reale Raspberry Pi Pico W (connesso fisicamente ai sensori). Per evitare di includere credenziali di rete e dettagli del broker MQTT nel codice sorgente tracciato (es. Git), le configurazioni di rete (SSID, Wi-Fi password ed IP del broker MQTT) sono state disaccoppiate in un file esterno denominato secrets.py:

# secrets.py
WIFI_SSID = "Nome_Della_Rete_WiFi"
WIFI_PASSWORD = "Password_Della_Rete_WiFi"
MQTT_BROKER = "192.168.1.50" # Indirizzo IP del PC Principale che ospita Mosquitto

Nel caso in cui si voglia continuare ad utilizzare l'emulatore Python per scopi di test o simulazione distribuita da un altro computer, lo script pico_emulator.py è stato parametrizzato per accettare l'indirizzo IP del broker come parametro a riga di comando:

python pico_emulator.py 192.168.1.50

Per isolare l'orchestratore cargoservice dai dettagli del protocollo MQTT, introduciamo un attore ponte (MQTT Adapter) nel contesto ctx_cargoservice che si occupa di convertire i messaggi MQTT in messaggi nativi QAK (es. distance(D)) e viceversa.

Architettura Logica Distribuita e Nodi di Deployment

In coerenza con la pianificazione e l'analisi effettuata nello Sprint 0, il deployment effettivo del sistema si distribuisce sui seguenti contesti fisici ed hardware:

  • PC Principale (Host PC): Rappresenta il nodo centrale computazionale del sistema. Su questa macchina fisica coesistono ed operano due diversi runtime:
    • Java Virtual Machine (JVM): Ospita il processo principale cargoservice (eseguito via ./gradlew run alla porta CoAP 8082). Questo processo avvia ed ospita nativamente il web server IOPortWebServer per la WebGUI dell'IOPort (porta 8081).
    • Docker Engine: Gestisce l'intera infrastruttura di simulazione e di comunicazione di rete tramite container isolati sulla stessa macchina:
      • Il broker MQTT mosquitto (porta 1883), impiegato per lo scambio messaggi con il microcontrollore.
      • Il pianificatore di movimenti autonomo robotsmart26 (contesto esterno ctxrobotsmart, porta 8020).
      • L'interfaccia di monitoraggio 2D del robot robotoutgui25 (porta 8085).
      • Il simulatore fisico 3D wenv (porte 8090/8091).
  • Web Browser (Client GUI): Rappresenta l'interfaccia utente finale per l'operatore/cliente. Può risiedere sia sulla stessa macchina, sia su un altro computer connesso alla stessa rete LAN locale. Dal browser vengono caricate e renderizzate la dashboard dell'IOPort (indirizzo http://<IP_PC_PRINCIPALE>:8081, che comunica con la JVM tramite HTTP/REST) e l'interfaccia 2D del robot (indirizzo http://<IP_PC_PRINCIPALE>:8085).
  • Raspberry Pi Pico W (Nodo Remoto): Rappresenta il microcontrollore hardware autonomo reale (contesto ctx_picow) connesso via Wi-Fi alla stessa rete del PC principale. Esegue lo script MicroPython pico_sonar_led.py per interfacciarsi fisicamente con il Sonar HC-SR04 e con il diodo LED, scambiando informazioni con il broker MQTT (porta 1883) ospitato sul PC principale. In caso di testing temporaneo o assenza di hardware, è possibile utilizzare l'emulatore locale pico_emulator.py configurato con l'IP del broker.

Modellazione del Comportamento del Robot e Coordinamento

Nel contesto dello Sprint 2, l'orchestratore cargoservice e l'attore cargorobot coordinano la movimentazione del robot nel rispetto dei requisiti di tema finale. Il robot esegue la transizione tra le aree logiche (IOPort, Slot5 e Slot di stoccaggio) e supporta la sospensione/ripristino dei movimenti in caso di guasto rilevato dal sonar remoto.

1. Sincronizzazione e Reset Iniziale

All'avvio, l'orchestratore invia un comando di reset per riallineare il planner logico di robotsmart26 con lo stato di startup del simulatore 3D (WEnv), forzando la posizione iniziale a (0,0) con direzione SUD (down):

State s0 initial {
    println("cargoservice | starting...") color blue
    [# SystemOutOfService = false #]
    forward ioport -m display_msg : display_msg(service_working)
    println("cargoservice | Sincronizzazione: resetto lo stato del robot nel planner a (0,0) SOUTH...") color blue
    forward robotsmart -m setrobotstate : setpos(0, 0, down)
    updateResource [# "state($SystemOutOfService,$Slot1Occupied,$Slot2Occupied,$Slot3Occupied,$Slot4Occupied,$ReservedSlot,$IOPortOccupied,$DisplayMsg)" #]
}

2. Mappatura delle Coordinate Logiche della Stiva

Le coordinate della stiva seguono la convenzione del planner A* espressa come (riga, colonna). Per ciascuno slot logico viene definita la coordinata di posizionamento adiacente libera ("accanto") al fine di prevenire collisioni con i container o gli ostacoli strutturali:

when (CurrentDest) {
    "home"   -> { TargetX = 0; TargetY = 0 } // Riga 0, Colonna 0
    "ioport" -> { TargetX = 4; TargetY = 0 } // Riga 4, Colonna 0 (IOPort)
    "slot5"  -> { TargetX = 2; TargetY = 5 } // Cella libera accanto a destra dello Slot 5 (2,4)
    "slot1"  -> { TargetX = 1; TargetY = 1 } // Cella libera accanto a sinistra dello Slot 1 (1,2)
    "slot2"  -> { TargetX = 2; TargetY = 3 } // Cella libera accanto sotto allo Slot 2 (1,3)
    "slot3"  -> { TargetX = 3; TargetY = 1 } // Cella libera accanto a sinistra dello Slot 3 (3,2)
    "slot4"  -> { TargetX = 4; TargetY = 3 } // Cella libera accanto sotto allo Slot 4 (3,3)
    else     -> { TargetX = 0; TargetY = 0 }
}

3. Sequenza Nominale e Ciclo di Lavoro

Il robot esegue la transizione lineare dei carichi passando per lo slot5 per la marcatura temporanea:

// 1. Spostamento all'IOPort per raccogliere il container
State robotExecution {
    [# CurrentDest = "ioport" #]
    request cargorobot -m move_robot : move_robot(ioport)
}
Transition t0 whenReply move_done -> robotAtIOPort

// 2. Spostamento a Slot 5 per etichettatura temporanea
State robotAtIOPort {
    [# CurrentDest = "slot5" #]
    request cargorobot -m move_robot : move_robot(slot5)
}
Transition t0 whenReply move_done -> robotAtSlot5

// 3. Posizionamento e attivazione del marcatore
State robotAtSlot5 {
    println("cargoservice | robot arrivato in slot5: poso temporaneamente per marcatura...") color green
    forward marker -m start_marking : start_marking($ReservedSlot)
}
Transition t0 whenMsg marking_done -> markingCompleted

// 4. Trasferimento nello slot di stoccaggio definitivo
State markingCompleted {
    [# CurrentDest = ReservedSlot #]
    println("cargoservice | marcatura completata: sposto il container in $ReservedSlot...") color green
    request cargorobot -m move_robot : move_robot($ReservedSlot)
}
Transition t0 whenReply move_done -> robotAtReservedSlot

4. Gestione delle Interruzioni (Out of Service) e Ripristino

Nel caso in cui il Sonar rilevi un errore (distanza > DFREE per 3s), viene emesso l'evento alarm per arrestare immediatamente il robot virtuale. Al ripristino delle condizioni normali, l'orchestratore ricalcola la transizione riprendendo il movimento verso l'ultimo target di destinazione memorizzato (CurrentDest):

State handleInterrupt {
    println("cargoservice | INTERRUPTION: Sonar failure reported.") color red
    emit alarm : alarm(sonar_failure) // Arresta robotsmart26
    [# SystemOutOfService = true; DisplayMsg = "out_of_service" #]
    updateResource [# "state(...)" #]
} Goto outOfService

State handleRecovery {
    println("cargoservice | RECOVERY: Sonar reports normal operation.") color green
    [# SystemOutOfService = false; DisplayMsg = "service_working" #]
    updateResource [# "state(...)" #]
} Goto working if [# ReservedSlot == "" #] else resumeActivity

State resumeActivity {
    println("cargoservice | resuming movement to destination: $CurrentDest")
}
Goto robotExecution if [# CurrentDest == "ioport" #] else checkSlot5Resuming

Test plans

I test dello Sprint 3 mirano a convalidare il funzionamento distribuito sulla rete LAN reale ed il comportamento di tolleranza ai guasti fisici:

Test Distribuito 1: Pressione Pushbutton da Browser Remoto (LAN)
Azione: Un browser connesso su un PC client differente (alla stessa rete LAN) effettua una POST HTTP verso http://<IP_PC_PRINCIPALE>:8081/load.
Risultato Atteso: Il display mostra la prenotazione dello slot ed il LED (remoto) inizia a lampeggiare.
Test Distribuito 2: Rilevamento Sonar Fisico su Raspberry Pi Pico W
Azione: Si posiziona un container ad una distanza < 10 cm davanti al sonar HC-SR04 connesso alla Pico W fisica remota.
Risultato Atteso: La Pico W invia le letture via Wi-Fi al broker MQTT sul PC principale. L'orchestratore attiva il robot virtuale ed invia il comando di lampeggio LED via MQTT. Il diodo LED sulla Pico W inizia a lampeggiare.
Test Distribuito 3: Tolleranza ai Guasti di Rete (Wi-Fi/Power Loss su Pico W)
Azione: Durante la movimentazione del carico, si spegne o scollega la Pico W dalla rete Wi-Fi.
Risultato Atteso: La perdita di connessione/heartbeat viene intercettata dall'adattatore MQTT che invia un messaggio di errore. L'orchestratore arresta immediatamente il robot virtuale per sicurezza ed imposta lo stato a out_of_service. Al ripristino dell'alimentazione/connessione della Pico W, il robot riprende il movimento da dove si era interrotto.

Organizzazione del processo di produzione

Pianificazione e compiti per lo sviluppo dello Sprint 3:

  • Configurazione e deploy dello script MicroPython (pico_sonar_led.py) ed isolamento credenziali in secrets.py sulla scheda fisica Raspberry Pi Pico W (Stima: 4 ore/uomo).
  • Parametrizzazione dell'emulatore Python per il passaggio dell'IP a riga di comando al fine di supportare test distribuiti da macchine terze (Stima: 2 ore/uomo).
  • Esecuzione del test di robustezza a guasti di rete (disconnessione temporanea del nodo sonar) (Stima: 3 ore/uomo).
  • Deployment distribuito reale e collaudo finale LAN multidevice (Stima: 4 ore/uomo).

Testing

Il collaudo è stato eseguito con successo connettendo una scheda hardware Raspberry Pi Pico W ed un PC secondario (tablet/smartphone) alla medesima rete Wi-Fi del PC principale:

  • Pressione del pushbutton da browser remoto ➔ Ricezione istantanea su JVM locale e prenotazione dello slot.
  • Rilevamento distanza da sonar HC-SR04 reale ➔ Spostamento del robot virtuale WEnv e marcatura.
  • Perdita di alimentazione Pico W ➔ Arresto immediato in sicurezza del robot ed out of service; al riavvio, il robot riprende correttamente il piano.

Deployment

Il deployment distribuito reale sulla rete LAN si compone dei seguenti passi operativi:

  1. Avvio Infrastruttura (PC Principale): Eseguire il comando docker compose up nella directory sprint3 del PC principale per avviare Mosquitto (porta 1883), WEnv (porte 8090/8091), robotoutgui25 (porta 8085) e robotsmart26 (porta 8020).
  2. Avvio del Core Service (PC Principale): Eseguire il comando ./gradlew run per avviare il servizio JVM cargoservice (porta 8082) ed il relativo server web dell'IOPort (porta 8081).
  3. Configurazione e Avvio del Nodo Remoto (Pico W):
    • Creare un file secrets.py sul microcontrollore Raspberry Pi Pico W contenente SSID, Password della rete Wi-Fi e l'indirizzo IP del PC Principale (es. 192.168.1.50) come broker MQTT.
    • Caricare ed eseguire lo script MicroPython src/pico/pico_sonar_led.py sulla scheda fisica Pico W.
    • *(In alternativa, per simulare da un PC terzo, eseguire il comando: python src/pico/pico_emulator.py <IP_PC_PRINCIPALE>).*
  4. Accesso Multidevice (PC Client Remoto / Smartphone): Aprire un browser web su un altro dispositivo connesso alla medesima rete locale ed accedere all'indirizzo http://<IP_PC_PRINCIPALE>:8081 per inviare i comandi di carico tramite l'IOPort Dashboard, ed all'indirizzo http://<IP_PC_PRINCIPALE>:8085 per visualizzare la griglia ed i movimenti del robot.
